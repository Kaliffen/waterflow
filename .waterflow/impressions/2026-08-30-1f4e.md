A claim about one declaration is written at that declaration and the record
keeps only its address, carried in `scope` as `path#Symbol` — the graft is
written during the build, never by the fold, and the comment carries no
provenance of any kind.

**The duplication is already happening, undirected.** In the `specbased` field
test, the `interrogate` record settling what a `Claim` is and the XML doc
comments on `Claim`, `ClaimHolder` and `ClaimSubject` are one document written
twice: household rejected as expressible but unnamed, resources and money
absent until `Resource` exists, co-ownership tolerated because adjudication
belongs to whoever acts on a claim. Five of the record's six sections are at the
declarations, near-verbatim, with no rule asking for it — because settling a
thing and documenting it are the same act. What grafting changes is only that
the store stops keeping the second copy, which is the one that goes stale.

**Impressions guide the water; the code is the channel.** A record exists to
steer work that is still moving. Once the claim is cut into the code it is held
by the code, and a record restating it is the current trying to remember a bed
it is standing in.

**The address goes in `scope`, not in a new field.** `scope` already points
store to code and is what every freshness check runs on; a graft is that field
narrowed to the exact site and made load-bearing. Nothing new is introduced, and
the direction that would rot — a comment naming a record — stays impossible,
because ids are superseded and folded and a comment would not know.

**No convention in the code.** The graft uses whatever doc idiom the codebase
already has, with no marker, no tag and no id. The symbol name lives in the
record, so nothing Waterflow invented ends up in somebody else's source. A
comment carries what is true now, timelessly: no revision, no atom or lane, no
date, no "this used to be".

**Build time, never fold time.** A fold that wrote into source would edit the
tree after the proof that closed it had run, and where doc comments are compiled
it could turn a proven build red after the run reported the work landed. So the
graft is written with the slice, compiled with it and proven with it; the fold
only notices it happened and empties the record in place.

**Emptied in place: not superseded, not moved.** Superseding says a claim was
replaced and moving says it was spent, and a grafted claim was neither — it was
transplanted and is still the current answer. Git holds the pre-graft body at
the commit that wrote it, and the same commit shows the reasoning arriving in
the code, so the trail reads as the transplant it was.

**Freshness collapses rather than complicating.** A grafted record's content is
read live, so it cannot drift; only its address can be wrong. Three states
become two — the declaration resolves, or the record is broken and the answer is
to go and look.

**What never grafts, and keeps its full expression:** a record with `scope: []`,
a decision not to build something, a claim about the shape between modules such
as a seam or a layering rule, a `watermark`, and a `goal`. In the `property-claim`
epic exactly one record of five would graft. The store does not empty out; it
loses the record that was going to duplicate `Claim.cs`.
